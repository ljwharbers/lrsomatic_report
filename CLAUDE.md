# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project does

Standalone R/Quarto reporting tool for the [LRSomatic](https://github.com/nf-core/lrsomatic) Nextflow pipeline. Takes a single-sample output directory and generates a self-contained HTML report for a clinical reader: an overview (key findings by gene list, genome-wide biomarkers), circos, copy number (incl. gene-level calls), genome instability (ShatterSeek, ecDNA), mutational signatures, small-variant and SV tables (Severus + SAVANA, Padfoot, ReConPlot) and QC. Research use only — the README says so, and so does the printed overview's footer. The README documents every clinical rule (tiers, CN thresholds, signature flags) in plain language: **a constant changed here must be changed there too.**

## Running the report

```bash
S=/path/to/sample-dir
Rscript bin/render_report.R \
  --sample-dir  $S \
  --sample-id   SAMPLE_ID \
  --sex         male \
  --reference   auto
```

Output defaults to `<sample-id>_report.html` in the current directory; the full small-variant table is written beside it as `<sample-id>_small_variants.tsv.gz` (the setup chunk writes it next to the rendered `.qmd`, `bin/render_report.R` moves it). `--embed slim|full` (default `slim`) picks which small-variant rows the HTML table embeds (`slim_variant_table()`; `variant_embed` in the setup chunk — `variant_table` stays the full table for every count). `--reference auto` reads `##contig` lines from the VEP somatic VCF to detect `t2t` vs `hg38`. Matched and tumour-only runs take the same command — every input is discovered from `--sample-dir`, and so is the run mode unless `--run-mode paired|tumour_only` states it (the pipeline passes it).

Add `--gene-panel lymphoid` (or `sarcoma`, or a TSV; repeatable) to open with a list ticked: the overview's key findings are only ever computed for genes on a list, and with none ticked they show nothing (see the overview bullet below). The pipeline passes `--gene-lists-dir` with its own copy of the builtin lists.

`--mode` and `--somatic-vcf` were **removed** (they used to be required). Run mode is derived from `has_normal`, and the VCF supplying VAF is discovered by `locate_outputs()`. Anything still passing them fails on an unknown option.

## R conventions

- Use `=` instead of `<-` for assignments.
- Data manipulation uses `data.table` (primary) and `dplyr` for secondary/display work.
- All R files in `R/` are `source()`d by the Quarto template — they are not packages or modules, just plain scripts.

## Code architecture

**Entry point:** `bin/render_report.R` — parses CLI args, auto-detects reference, calls `locate_outputs()`, then drives `quarto::quarto_render()` on `templates/per_sample.qmd`.

**Template:** `templates/per_sample.qmd` — the Quarto document. All R source files are re-sourced here via `params$repo_dir`. Receives a `params$outputs` named list (from `locate_outputs()`) containing file paths for every tool's output.

## Section-module contract

Report sections are being migrated (opportunistically, one at a time) to a self-contained
module pattern so a new tool output can be added without touching `locate_outputs.R` or the
setup chunk of `per_sample.qmd`. `R/sections/sv.R` is the reference implementation.

To add a new section:

1. Create `R/sections/<id>.R` calling `register_section(list(...))` with:
   - `id`, `title`
   - `locate(sample_dir, sample_id)` — owns this section's own path discovery (globs/`pick()`),
     returns a named list of inputs (e.g. a `callers` list if multiple tools produce this
     output type, following the pattern in `sv.R`).
   - `parse(inputs, section_data)` — returns one data object for this section, or an
     empty/NULL-ish result if there's nothing to show. `section_data` holds already-parsed
     sections (registration order = parse order), for sections that depend on another (e.g.
     circos reads `SECTION_DATA$sv$circos`). A `parse` may declare a third argument, `ctx`
     (sample_id, sample_dir, reference, sex, all_panels, chromosomes, chrom_lens, cytobands,
     embed, repo_dir, outputs — documented in `R/sections.R`); it is passed only when
     `length(formals(s$parse)) >= 3`, so two-argument modules are unaffected.
   - Parse order is `SECTION_ORDER` in `R/sections.R` (sv, whatshap, cna, shatterseek, ecdna,
     reconplot, signatures), applied by `section_files()`; a file not named there is sourced
     after them, alphabetically. Add a new id there if another section reads its result.
2. Create `templates/sections/_<id>.qmd` — reads `SECTION_DATA[["<id>"]]`, renders it, and uses
   `section_notice(msg)` (from `R/sections.R`) for the "nothing to show" case instead of a raw
   `tags$div(...)`.
3. Add `{{< include sections/_<id>.qmd >}}` to `templates/per_sample.qmd` in display order —
   or, for a subsection of an existing section, to that section's own `.qmd` — `_qc.qmd` includes
   `_whatshap.qmd` that way. Nested include paths are still resolved relative to the **root**
   document (`templates/per_sample.qmd`), not to the including file, so a nested include keeps
   the same `sections/_<id>.qmd` prefix a top-level one has.

`R/sections.R` holds the registry (`SECTIONS`, populated at source time) and `section_notice()`.
The setup chunk in `per_sample.qmd` loads the reference data, sources every file in
`R/sections/` in `SECTION_ORDER`, then runs
`SECTION_DATA[[s$id]] = run_section_parse(s, s$locate(sample_dir, sample_id), SECTION_DATA, ctx)`
for each registered section. Sections not yet migrated (SNV, QC, circos, and the ASCAT plots
plus the capped ASCAT segments the circos draws) keep parsing directly from `outputs$<key>` in
the setup chunk — migrate them the same way when they next need a change.

Contract traps:

- **`SECTION_DATA[[id]] = NULL` leaves no entry**, it does not store a NULL. Every reader must
  therefore treat "absent" and "NULL" alike (`SECTION_DATA$cna` is `NULL` either way, but
  `names(SECTION_DATA)` will not list it). ShatterSeek and ecDNA return `list(status = "not_run")`
  instead of `NULL` precisely so the overview can tell "ran, found nothing" from "not run".
- **Tool output columns are resolved, not indexed.** New parsers take a canonical → candidates
  spec through `resolve_columns()` (exact names first, then a normalised match that never reuses
  a claimed column — Padfoot's `pos_1` and `Pos_1` differ only in case). A missing optional
  column must make a rule unable to fire, never error.
- **Static plots go through `embed_svg_plot(p, width, height)`** (ggplot, or a zero-argument
  base-graphics function) → base64 SVG `<img>`, the same route as the circos; no new graphics
  dependency, and the report stays self-contained. Raw HTML emitted from a `results='asis'` chunk
  inside a tabset/callout fence goes through a ```` ```{=html} ```` block so Pandoc leaves the
  base64 alone (`_reconplot.qmd`, `_signatures.qmd`).
- **Plain HTML tables need `data-quarto-disable-processing="true"`** (key findings, gene-level CN),
  or Quarto adds Bootstrap classes and odd/even striping that does not follow rows the JS hides.
- **Quarto moves a heading's `{#id}` onto the wrapping `<section>`.** An element that needs a
  stable id of its own takes a different one — the key-findings root is `#kf-root`, not
  `#key-findings`.

One deliberate exception: the SNV section was reworked without being migrated. Its
`vep_somatic` path is needed by `bin/render_report.R` for `--reference auto` *before* Quarto
sources any section module, so moving that discovery into a section module would drag
reference auto-detection into the change. Migrate it only together with a plan for that.

## Key design details

- **VEP file format:** `outputs$vep_somatic` (`*_SOMATIC_VEP.vcf.gz`) ships in either of two incompatible formats depending on the VEP invocation — the filename doesn't tell you which. `parse_vep()` sniffs the header (`#Uploaded_variation` vs `#CHROM`) and dispatches accordingly:
  - `parse_vep_text()` — VEP *default text output* (tab-delimited, `##`-commented header, column header line starts with `#Uploaded_variation`, NOT a VCF). The `Extra` column holds semicolon-delimited `KEY=VALUE` pairs parsed by `parse_extra_kv`.
  - `parse_vep_vcf()` — genuine VCF (`--vcf` VEP output) with annotations in a pipe-delimited `CSQ` INFO field; the field order is read from the `##INFO=<ID=CSQ,...Format: ...>` header line rather than hard-coded.
  Both return the same column contract (`chrom, pos, ref, alt, symbol, gene_id, consequence, impact, hgvsp, existing, dbsnp, cosmic, caller, coord_space`, plus the optional annotation columns below); `derive_dbsnp_cosmic()` and `add_vep_annotations()` are shared between them.
- **The plugin annotation columns are resolved from the header, and a column exists only when its source does.** LRSomatic annotates with VEP plugins whose CSQ field names differ by assembly: on GRCh38 the cache's own `SIFT`/`PolyPhen` (`deleterious(0.01)`), `AlphaMissense` (`am_class`, `am_pathogenicity`), CADD, REVEL and EVE; on T2T the cache has **no** SIFT, PolyPhen, dbSNP, COSMIC or population data at all, so `PolyPhen_SIFT` supplies `SIFT_pred`/`SIFT_score`/`PolyPhen_humvar_pred`/`_score` and `AlphaMissenseProtein` the same `am_*` fields; a ClinVar `--custom` track adds `ClinVar`/`ClinVar_CLNSIG` on both. The parsers used to read a fixed eight fields, so on T2T `sift`/`polyphen` rendered empty while the data sat three fields to the right, and no plugin output reached the report on either assembly. `VEP_ANNOTATION_FIELDS` (`R/parse_smallvariants.R`) maps each report column to its candidate fields, first present wins (`ClinVar_CLNSIG` over the cache's `CLIN_SIG`; humVar, not humDiv, because that is what the built-in PolyPhen reports), and `add_vep_annotations()` applies it identically to CSQ fields and `Extra` keys. Class and score are **separate columns** (`sift`/`sift_score`, `am_class`/`am_score`, …): the class gets a tickbox filter, the score sorts as a number, and the built-in `pred(score)` form is split to match. The rule for presence is *declared, not populated*: a field absent from the CSQ `Format:` (or, on the text path, from the `## KEY :` header lines and every row) produces **no column**, because the plugin did not run; a declared field that is empty stays as an all-NA column, because it ran and found nothing. `dbsnp`/`cosmic` follow the same rule via `vep_cache_sources()`, which reads the `##VEP=` line in a VCF (`dbSNP="156" COSMIC="99"` on GRCh38, neither on T2T) and the `## dbSNP version 156` / `## COSMIC version 99` lines in text output — they were two permanently empty columns on every T2T report. **The text scan is anchored at line start, and has to be**: every VEP text header describes its own Extra keys, and one of those descriptions is `## CLIN_SIG : ClinVar clinical significance of the dbSNP variant`, so an unanchored `dbSNP[= ]` matched on a T2T header that carries no variation data at all — keeping the empty `dbsnp` column while `cosmic` correctly vanished beside it, and listing dbSNP as *present* in the footnote. The resolution travels as `attr(, "vep_fields")` through `build_variant_table()` (`merge()`/`unique()` drop attributes, so it is re-attached), and `_smallvariants.qmd` prints an **Annotation sources** footnote from `vep_annotation_summary()` naming what was present and, more importantly, what was not — an absent `am_class` must read as "plugin not run", not "nothing pathogenic". `PATHOGENIC_CLASSES` is tinted in a third colour, outside both the impact palette and the `callers` flag — by `styleEqual()` for the single-valued class columns, but by a **token-aware `createdCell`** for `clinvar`, which is the one multi-token class column (`&`→`,`, facet sep `,`): `styleEqual()` matches whole cells, so `Pathogenic,risk_factor` would filter correctly under the tickbox and render plain. That is why `window.PATHOGENIC_CLASSES` is published alongside `SNV_FACETS`, and why `equal_cols` is `class_cols` minus `clinvar`. `clinvar_id` gets the same `&`→`,` rewrite so its link render can emit one ClinVar link per id. Renaming is the hazard here as elsewhere: `snv_facet_cols`, `class_cols` and `VEP_SCORE_COLUMNS` all name these columns, and `js_facet_defs()` skipping a facet is only a `console.info`.
- **In VEP text output `Existing_variation` is a column, not an `Extra` key.** `parse_vep_text()` read it with `extract_extra_key(Extra, "Existing_variation")`, which is never set there — so `existing`, and with it `dbsnp` and `cosmic`, were **100% NA on every text report**, silently: measured on a real GRCh38 text output, 7,344 of 9,028 rows carry an rs ID and 80 a COSV ID in that column, and 0 rows have `Existing_variation=` anywhere in `Extra`. The header says the cache has both, so the columns were kept and the **Annotation sources** footnote listed dbSNP and COSMIC as present over two empty columns. It is now read from the column, with `-`/`""` normalised to NA. The CSQ path was always fine — there `Existing_variation` really is a CSQ field. Related: the "annotation key present in a row but not declared in the header" scan is one `grepl()` alternation over `setdiff(cands, declared)` with the matches extracted only from the rows that hit; one `grepl()` per candidate key cost 8.8 s of every render at 171k rows against 0.8 s now.
- **A CSQ-format "somatic" VEP VCF may be a merged multi-caller VCF.** This applies to the `parse_vep_vcf()` path only — the pipeline's default `vep_args` produce text output (somatic-only, 27k–167k rows on real samples), and a `--vcf` run is what can carry germline calls (DeepVariant, Clair3) into `*_SOMATIC_VEP.vcf.gz` alongside the somatic ones — on a real sample that's ~99% of the records — distinguished only by an `INFO/CALLER` tag. `parse_vep_vcf()` therefore keeps only `FILTER` ∈ {`PASS`, `.`} records whose caller is in `SOMATIC_CALLERS` (`clairs`, `clairs-to`, `clairsto`, `deepsomatic` — ClairS is tagged `clairs` in matched mode and `clairs-to` in tumour-only). The caller filter is applied **only when a `##INFO=<ID=CALLER` header line is present**, so older single-caller VEP VCFs aren't filtered to nothing. This filter is also what keeps the parse tractable: unfiltered it is ~5.4M variants and ~7 minutes.
- **Missing files are graceful:** Every parser returns `NULL` if its input file is absent; the template shows a "not available" notice per section.
- **Run mode is derived unless declared:** `locate_outputs()` sets `mode = if (has_normal) "matched" else "tumour-only"`, and `apply_run_mode()` replaces it with `--run-mode` (`paired` → `matched`, `tumour_only` → `tumour-only`; `mode_source` says which) — a pair that skipped every QC tool has no normal-side file. `has_normal` stays file-based. Its consumers are the hero badge in `_header.qmd` and the overview's tumour-only caveat (`build_overview()` reads `ctx$outputs$mode`); `_qc.qmd` reads `has_normal` directly.
- **Small variants use the VEP output as the single source of truth.** The VEP file defines the variant set; VAF/DP/GT/PS are joined from the VCF VEP annotated, which `locate_outputs()` resolves into `somatic_vaf_vcf` by a fallback chain: `variants/phased/somatic_smallvariants.vcf.gz` (what the pipeline actually feeds VEP, and the only rung carrying `FORMAT/PS`) → `variants/clairs{,to}/somatic.vcf.gz` → any non-germline VCF in those directories → `NULL`. Only ~20 of the sample dirs on disk have `variants/phased/`, hence the chain. `--somatic-vcf` and the per-caller `vaf_clairs`/`vaf_clairsto`/`vaf_deepsomatic` columns are gone; the table now has plain `vaf`, `dp`, `gt`, `ps`.
- **That single `vaf` column is ambiguous after a consensus merge, and the report says so rather than fixing it.** `somatic_vaf_vcf` resolves to *one* file, and the LRSomatic module stages the pipeline's final somatic VCF at exactly that path (which is also what drives run-mode detection). When several somatic callers were combined by consensus, that VCF's FORMAT fields come from whichever caller won each variant — so `vaf`/`dp`/`gt`/`ps` need not correspond to the `callers` value in the same row. The variant **set** is unaffected: it comes from the VEP file, where `INFO/CALLER` is read per record. v1.2.0 makes this visible instead of joining per caller: `vaf_provenance()` (`R/parse_smallvariants.R`) reads just the VCF header for its path and any `##source=` line, and `templates/sections/_smallvariants.qmd` prints a `.table-footnote` naming the file, the join coverage (`n_vaf` of `nrow(variant_table)` — a near-zero count here is how a broken `variant_key()` surfaces), and, when `n_multi > 0`, the consensus caveat plus highlighting on the multi-caller `callers` cells. **`n_multi` is always 0 on the VEP text path**, which carries no per-variant caller; the caveat therefore fires only on the CSQ path, which is exactly where the ambiguity lives. Joining per caller instead would need `modules/local/lrsomaticreport/main.nf` to stage each caller's VCF — a module input-tuple change, so it was deliberately not done here.
- **VEP and the VCF disagree about indels — `variant_key()` reconciles them.** VEP always reports an indel one base right of the VCF anchor, and depending on version writes either the raw VCF allele pair (`chr1_1871655_TG/T`) or its own trimmed dash form (`chr1_192937_AATA/-`). Both are normalised to *trimmed alleles at anchor+1* before joining. Getting this wrong is silent — it produces `NA` VAF rather than an error — and it was: before this key existed, **0% of deletions joined**. Verified at 100% across all three variant classes on 10 real samples covering both notations. This also requires `parse_vep_text()` to take `chrom`/`pos` from `variant_id`, **not** from `Location`: for a dash-form insertion, `Location`'s start is one base left of the position `variant_id` names, and mixing the two sources is what caused the original breakage.
- **Which coordinate space a VEP table is in is declared by its parser, not assumed by the joiner.** The two parsers genuinely differ: `parse_vep_text()` reads coordinates from `variant_id` (VEP space — indels already shifted, possibly dash-form), while `parse_vep_vcf()` reads the VCF's own `POS`/`REF`/`ALT` (VCF space — the *original* input coordinate, which VEP does not rewrite in `--vcf` mode). Each sets a `coord_space` column and `build_variant_table()` keys `variant_key()` from it. Hard-coding `space = "vep"` there shifted only one side of the key on the CSQ path, so **no indel could ever join** and its `vaf`/`dp`/`gt`/`ps` came back silently `NA` — measured on COLO829-ONT as 717 of 49,003 rows, exactly the 395 deletions + 322 insertions. Now 100% on all three classes. `parse_vep_vcf()` deliberately does **not** normalise into VEP space: that would change the `pos`/`ref`/`alt` a reader *sees* for every CSQ-path indel. Only the key changes.
- **The allele-fraction FORMAT tag is not always `AF`.** LRSomatic renames it by prioritised caller — `STANDARDIZE_AF` in `subworkflows/local/small_variant_consensus.nf` maps `AF → VAF` for `deepvariant`/`deepsomatic` and `VAF → AF` for `clair`, and a `consensus` merge skips the renaming entirely — so both names reach `parse_caller_vcf()`. It hard-coded `AF`, which is why a DeepSomatic run rendered an **entirely empty VAF column** while `dp`/`gt` beside it were fine (same merge, same key — the join was never the problem). `allele_fraction()` now tries `AF`, then `VAF`, then derives from `AD`. The pipeline default is `prioritize_caller_somatic = 'clair'`, i.e. `AF`, which is why this went unnoticed.
- **The sample column is chosen by name.** `parse_caller_vcf()` read column 10 positionally; on a matched two-sample VCF where NORMAL sorts first that reports the **normal's** VAF/DP for every somatic variant, with no error and nothing in the report to reveal it. `pick_sample_column()` prefers the sample named for the report, then the first not named like a normal, and warns when it has to guess. `vaf_provenance()` names the chosen sample in the footnote — but only when the VCF held more than one, since that is the only case where the choice can be wrong.
- **One row per rearrangement, not per breakend record.** Severus writes both sides of a rearrangement as separate `_1`/`_2` records linked by `INFO/MATE_ID` (verified 1:1 in every sample checked), and tags single breakends `sBND`, which fails a bare `== "BND"` test. `parse_sv_vcf(f, caller)` (for Severus via its wrapper `parse_severus_somatic_records()`) collapses mate pairs into one row carrying `chrom_a/pos_a` **and** `chrom_b/pos_b`, derives `svclass` (`translocation` vs `intra-chr breakend` vs `single breakend` vs the plain SV type — 24 of 35 collapsed BNDs in COLO829-ONT are intra-chromosomal, which the old code filed under "translocations"), and is the single VCF read per caller behind the table, the SV count and the circos links, so those three cannot disagree. The partner locus comes from the ALT bracket notation — matched **reference-agnostically**, because the old `chr[^:]+` pattern would drop every BND on a bare-contig reference — and is filled in even for a record whose mate was filtered out. Groups that aren't exactly a pair stay singletons rather than being dropped. Three crashes were latent along this path and are now guarded: `END`/`SVLEN` are created unconditionally (a BND/INS-only VCF has neither), `.info_val()` is length-preserving (bare `regmatches()` drops non-matching elements — an error waiting for the first optional INFO key), and `ensure_chr_prefix()` coerces its input (`fread` types a bare-contig `CHROM` as integer, and `ifelse` on an all-NA test returns logical NA).
- **The SV table's breakend genes are display context; they are not the filter key.** `build_sv_table_from_vep()` joins the VEP SV VCF **on record ID**, with a locus key only as a fallback for annotation files whose IDs don't overlap at all (IDs matched 100% in every sample checked) — the old locus join leaked annotations between distinct records starting at the same base. Both breakends are annotated, giving `gene_a`/`gene_b` in place of the single `gene_hits`; `consequence`/`impact` come from the higher-impact side. The choice of key is made once for the whole table, not per side: per-side would ID-match side A and silently locus-match side B. `parse_sv_vcf()` applies no FILTER filter while `parse_vep_vcf()` keeps only `PASS`/`.`, so some rows legitimately have no symbols. A missing VEP SV VCF empties those columns but keeps every SV — panel matching is positional, so the section still filters correctly, and the gene-annotated TSV fallback (`build_sv_table()`) is mapped onto the same schema for the same reason.
- **The SV table is stored bedpe-shaped and displayed span-shaped, and `svclass` — not the contig — decides which a row is.** `chrom_a/pos_a/chrom_b/pos_b` is the only schema a translocation fits, and every consumer reads it (`sv_panel_hits()`, the `svPanelHits()` JS mirror, `bnd_links()`). But it is the wrong *reading* for most rows: a DEL's two records are its own start and end, and its `gene_a`/`gene_b` are the genes at either edge of one span — six columns of A/B ceremony for what is really `chrom, start, end, genes`. `sv_display_columns()` (`R/parse_severus.R`) therefore derives `locus`, `size` and `genes`, and `_sv.qmd` hides the raw columns (`visible = FALSE`) instead of dropping them. **The branch is on `SV_JUNCTION_CLASSES`, not on `chrom_b == chrom_a`**: `parse_sv_vcf()` fills `chrom_b = chrom_a`, `pos_b = INFO/END` for DEL/DUP/INV/INS, so same-contig is equally true of an intra-chromosomal breakend — and there the two loci are a *junction*, not a span the variant swallows. Keying off the contig would hand 24 of COLO829-ONT's 35 BNDs a start, an end and a size they do not have; a junction's `size` is deliberately blank for the same reason. `genes` merges both sides for a span and labels them `A:`/`B:` for a junction, where which partner carries which gene is the whole point. Three things this rests on:
  - **It is a display-layer change only, because the whole JS layer resolves columns by name.** `window.SV_COLS` is a name→index map emitted *after* `setcolorder`, `idx0()` resolves colDef targets by name at render time, and `svPanelHits()`/`rowId()` read through name lookups — so reordering is free and DataTables hands render and search callbacks the full row array, invisible columns included. Nothing in `sv_panel_hits()`, `bnd_circos.js`, the panel cards or the row-click chain moved. **Renaming** those columns is the hazard, not reordering: `sv_panel_hits()` reads `sv_table$chrom_a` unguarded, and `bnd_links()`'s all-or-nothing name guard makes the circos vanish *silently*.
  - **`locus` and `size` sort on hidden companion columns.** As formatted strings they sort lexically — `chr2:` after `chr13:`, `613 kb` after `1.2 Mb` — so `locus_sort` (`%03d:%011.0f` of the chromosome's rank in `chromosomes_for_sex()`, off-panel contigs last) and `size_bp` exist purely as sort keys, redirected via a DT render that intercepts only `type === 'sort'`/`'type'`. `display`, `filter` and `export` all fall through to the readable string, which is what lets a per-column search for `chr8` match a translocation on **either** side — the old `chrom_a` box could not. Positions are formatted with `formatC(big.mark = ",")`, never vectorised `format()`, which pads to a common width (the same trap `js_num()` documents above).
  - **The export orthogonal is `"export"`, and the column selector is explicit.** It was `"sort"`, which would now export `locus` as a zero-padded key; no renderer recognises `"export"`, so all of them fall through to the full untruncated string. `columns = seq_len(ncol(sv_display)) - 1L` is passed explicitly because Buttons defaults to `:visible`, which would silently drop the raw coordinate columns from the CSV.
- **Phasing statistics are germline.** `R/sections/whatshap.R` reads `qc/whatshap_stats/*_whatshap_stats.tsv`, which the pipeline generates from the phased *germline* VCF — every row's `file_name` is `germline_smallvariants.vcf.gz`. The header line starts with `#`, so `setnames(dt, sub("^#", "", names(dt)))` is required after `fread`, and `bp_per_block_sum` arrives as `integer64` and must be widened. `phased_fraction` is a 0–1 fraction. `qc/whatshap_stats/` is *not* `<type>`-scoped, unlike the rest of `qc/`, so a plain recursive match is correct. The section renders as a collapsible **Phasing** block inside **QC details** rather than as a top-level section: `_whatshap.qmd` carries its own `::: {.callout-note collapse="true"}` fence and an `###` heading, and `_qc.qmd` includes it as its last block, so it matches its three sibling QC blocks. It is still a registered section module, so `SECTION_DATA$whatshap` — which the overview's "Phased variants" card (Sequencing row, `_overview.qmd`) reads — is unaffected by where it is drawn. The card goes through `whatshap_totals()` (`R/sections/whatshap.R`) rather than reaching into `$all` itself, and shows the phased **count** with the fraction and the denominator as its subtitle (`2,864,966` / `92.6% of 3,092,264 heterozygous · germline, WhatsHap` — whatshap's `phased_fraction` is phased / `heterozygous_variants`, so that is the denominator shown; it was `variants` before 2.0.1, which put 92.6 % next to a count it was not a fraction of) — the label says "variants", so a bare percentage was the wrong number under it. Three things that helper fixes. It reads every field through a `names()` guard, because a TSV with an `ALL` row but no `phased_fraction` column made the old inline expression **error**, not fall back: `is.na(NULL)` is `logical(0)`, and `&&` on it is an error, not `FALSE`. It **sums the per-chromosome rows when whatshap wrote no `ALL` row**, which was previously a silent `N/A` sitting under a Phasing table that rendered perfectly. And it recomputes `phased / heterozygous_variants` (`phased / variants` only without a heterozygous count, `denominator` says which) whenever the fraction is missing or the rows were summed, rather than averaging the per-chromosome fractions. It returns `NULL` when there is nothing to total, and the card is then **omitted rather than rendered as `N/A`** — `htmltools` drops a `NULL` child, `.metric-grid` is `auto-fit` so the group re-flows to three cards, and the absence is already reported where it belongs, by the Phasing block's own "not found" notice. `DLBCL3_pooled` is that case: a tumour-only ClairS-TO run with no `qc/whatshap_stats/`, no `variants/phased/` and no germline calls at all, so no code change can put a number in that box.
- **No methylation section, by decision.** The only methylation output the pipeline publishes is `methylation/<type>/modkit_pileup/<id>.bed.gz` — 38–42 GB gzipped per sample, unfiltered, no tabix index — which cannot be read at render time. `modkit pileup` already runs `--bgzf`, so publishing a `tabix -p bed` index alongside it would unblock this (region queries measured ~0.16 s/Mb on an indexed pileup). The ~1 GB indexed pileups and `*_island_methylation_summary*.tsv` files present under some sample dirs are **ad-hoc analysis outputs, not pipeline outputs** — inconsistent filenames, ambiguous suffix variants, partial coverage — so they are deliberately not wired up. A per-gene methylation view would additionally need a gene-coordinate asset for both references; `assets/references/` has only cytobands and chromosome lengths.
- **QC discovery is one ranked pick, not a first hit — `pick_qc()` in `locate_outputs()`.** Several files legitimately match one basename pattern: cramino runs on the aligned BAM *and* on each uBAM, all writing `<id>_<type>_cramino.txt`, so the old alphabetical first hit could be a raw-read report. `pick_qc(pattern, side, prefer, avoid, within)` lists `sample_dir` once (relative paths with a leading `/`, so neither the side test nor a preference can match `sample_dir`'s own path — a sample dir under a `.../normal/...` path is otherwise read as all normal-side), keeps the `side` (`/normal/` in the path, or not), and ranks hits: under `/qc/` first, then each `prefer` regex in order (`/cramino_aln/`, `/samtools/`, `/mosdepth/`), then away from `avoid` (`/cramino_ubam`). `within` is a hard requirement, used only for loose patterns: mosdepth has two namings, `<prefix>.mosdepth.summary.txt` (older) and `<id>_<type>.summary.txt` (current), and the bare `.summary.txt` form is accepted only under `qc/` or `mosdepth/`. In the pipeline-staged layout (flat symlinks in `qc/tumor/`, `qc/normal/`, no tool subdirectories) the preferences simply have nothing to re-rank. `has_normal` — and with it `mode` — is any normal-side QC file found, not `dir.exists()`.
- **QC parsers match keys exactly, because the loose matches were silently wrong.** cramino 2.0 writes `N50 aligned`, `N75 aligned`, … after the full-read-length rows, so `grepl("N50")` was right only by row order; `CRAMINO_KEYS` maps each field to exact keys (text before the first tab, case-insensitive), with alternatives for renamed ones (`% from total reads` in 2.0, `% from total alignments` in 1.x). The `*_aligned` fields are NA on 1.x, which is how `_qc.qmd` decides whether to label the N50 "full read length". samtools flagstat ≥ 1.13 has `primary mapped (` after `mapped (`, so the old substring test let the later line win and the report's "mapped" was the *primary* figure; `FLAGSTAT_LABELS` matches the whole label, `mapped` now counts every mapped record (secondary/supplementary included) and `primary_mapped` is its own row — a user-visible change, recorded in the README. A 0-byte file (stub runs, an interrupted publish) parses to the empty result, not an error: `fread` returns a column-less table, so `parse_mosdepth_summary()` checks for its columns before indexing `chrom`.
- **Gene-panel filtering is opt-in, and only client-side.** `--gene-panel` defaults to `none` — LRSomatic is a general somatic pipeline, so hiding non-panel variants on load is wrong for most runs. Three-way resolution in `resolve_gene_panel()`: the `none` sentinel returns `NULL`, a builtin name or an existing TSV path loads, and **anything else is an error** so a typo can't silently produce an unfiltered report. Tables are always *built* unfiltered and filtered in the browser; `--gene-panel` only picks which panels are checked on load, and a user-supplied TSV is registered alongside the builtins so it can be selected (previously the fallback silently reselected `lymphoid` for any non-builtin value). **There are no "Panel variants"/"Panel SVs" hero cards any more.** They were either dead or lying: `--gene-panel` defaults to `none`, so on most runs both read `N/A`, and when a panel *was* selected they stayed frozen at the load-time selection while the reader ticked panel chips, because only `#panel-variant-count` in the filter bar is live (`updateCount()` on every `draw.dt`). Removing them took `panels`, `panel_genes`, `have_panel`, `n_panel_vars`, `sv_panel_hit` and `n_panel_svs` out of the setup chunk with them — and with those, `resolve_selected_panels()` itself, whose only callers they were. That loses no validation: `bin/render_report.R` already aborts before Quarto starts on a builtin that fails against the rendered reference, on an unloadable TSV and on a name that is neither.
- **`--gene-panel` is repeatable, and several panels union.** optparse has no `action = "append"` — a repeated option silently keeps only the last value — so `extract_repeated_option()` (`R/utils.R`) strips every occurrence out of `commandArgs()` before `parse_args()` sees it, and the `make_option()` entry survives in `option_list` only so `--help` documents the flag. `none` mixed with a real panel is an error rather than a case where one quietly wins, and duplicate paths are collapsed by `normalizePath()` before registration; a basename collision walks `-custom`, `-custom2`, … via `unique_panel_name()`, since the old one-shot suffix could only survive one. `default_panel` (a string) is now `default_panels` (a vector) end to end. **Nothing server-side resolves the selection any more** — the panel hero cards were its only readers, so `panels`/`panel_genes` and `resolve_selected_panels()` are gone with them, and which panels are checked on load travels to the browser as `DEFAULT_PANELS` and nowhere else. What survives of that helper's rationale: a panel that has round-tripped through Quarto's YAML comes back with **list-typed** vectors where it had atomic ones, because YAML reads a sequence as a list and a scalar as a scalar. The one live consumer is `bnd_panel_genes(bnd_drawn, params$all_panels)` (`_sv.qmd`) → `panel_intervals()`, which copes: it reads `has_coords` (a scalar, so still logical) and coerces the rest with `as.character`/`as.integer`, which flatten a list of length-1 elements. Anything new that reads a panel's `genes` straight off `params$all_panels` does not get that for free. In the browser, **no panel checked is the unfiltered state** — there is no `__all__` entry in the UI, so the sentinel now lives only in `bin/render_report.R` and the `params:` default of `per_sample.qmd`, not in three places. `js_vec()` emits `DEFAULT_PANELS`, because `paste(collapse = ",")` on an empty vector yields `[""]` — one panel named `""`, unfiltered only by accident.
- **The panel selector is checkboxes, and the SV footnote follows them.** `_gene_filter.qmd` emits one `.panel-toggle` chip per registered panel plus `Custom…`; `.is-on` is toggled from JS rather than styled off `:checked`, so a programmatic Clear cannot leave a chip disagreeing with its box. The handler in `per_sample.qmd` reads `state.panels` back off the rendered `checked` attributes on load instead of trusting `DEFAULT_PANELS`. `_sv.qmd` emits one `<span class="sv-panel-note" data-panel="…" hidden>` per **registered** panel — not per selected one — plus `__none__`, `__custom__` and `__multi__` fixed notes, and `window.updatePanelNotes()` shows the matching ones; the previous single server-rendered note went stale the moment the reader switched panels. It uses the `hidden` attribute, not inline `display`, so the print stylesheet isn't fought over it.
- **A cell rendered from panel state has to be *invalidated*, not just redrawn.** DataTables renders a cell exactly once, when it creates the row's `<tr>` (`_fnCreateTr` returns immediately if `nTr` is already set), and the SV table is `deferRender` + `Scroller`, so a row node is created the first time it scrolls into view and reused for every draw after that. `panel_hit` carries no data of its own -- its render calls `svPanelHitLabel()` against `window.svPanelState` -- so a row drawn while nothing was ticked kept a blank cell once the reader ticked a panel, and with `DEFAULT_PANELS` empty on most runs that is the entire first screenful. The `ext.search` predicate runs per draw and was right the whole time, which is what made it read as the filter and the label disagreeing about the same gene: a breakend filtered *in* by `MYC` 139 kb away, shown with no reason why, next to rows scrolled into view later that were labelled correctly. `redraw()` therefore calls `rows().invalidate("data").draw()` on the SV table, which rewrites every created cell from the current render and drops the stale `_aSortData`/`_aFilterData` with it, so the column's own search box and sort follow too; the plain `.draw()` beside it is enough for the small-variant table only because nothing there renders off panel state. Same class as the panel hero cards that were removed for freezing at the load-time selection -- re-filtering is not re-rendering.
- **The categorical columns filter by tickbox, not by typing, and the values come from R.** DT's `filter = "top"` gives every column a free-text box, which only helps a reader who already knows what is in the column — nobody remembers the ~30 VEP consequence terms, and a zero-row table then reads as "no such variants" rather than "no such spelling". `assets/js/facet_filter.js` replaces that box with a checkbox dropdown for `consequence`/`impact`/`callers` and the plugin class columns `sift`/`polyphen`/`am_class`/`clinvar`/`eve_class` (small variants; `snv_facet_cols` in `_smallvariants.qmd`) and `svclass`/`svtype`/`impact`/`consequence`/`caller`, plus `padfoot_impact` when Padfoot ran (SVs; `sv_facet_cols` in `_sv.qmd`), listing the values actually present with per-value row counts; every other column keeps its text box, and the table's own global search box still does substring across all columns. **`SearchPanes` was rejected** even though DT bundles it: it needs an `r-dt` version pin in `recipe/meta.yaml` *and* the pipeline's `environment.yml`, i.e. a rebuild of both Wave artifacts, which is exactly the cost this feature is not worth. **DT factor columns were rejected** because their filter matches whole values, which is wrong for a multi-token cell, and because making the column a factor is a data change that touches `styleEqual()` and the orthogonal renders. The `#facet-clear` button that resets every ticked value lives in `.panel-controls` next to the panel `#panel-clear` — a ticked filter can be scrolled out of sight under `scrollY`, and there it inherits the print hiding for free — and the two **share the `.panel-controls__clear` style**, so restyling one restyles both.
  - **The values are enumerated in R** (`js_facet_defs()`, `R/utils.R`) because the small-variant table is 27k–167k rows; the payload is `window.SNV_FACETS`/`window.SV_FACETS`, emitted from the same `results='asis'` prepare chunks that already publish `SNV_COLS`/`SV_COLS`, hand-serialised with `js_quote`/`js_num` for the same no-jsonlite reason as `window.BND_DATA`. Counts are **rows per distinct token**, so a split column's counts sum to more than `nrow()`. What R emits is the **unfiltered baseline** and the value ordering; the number actually shown is recomputed per pass — see the next bullet.
  - **The displayed count is live, and it excludes the column's own ticks.** A static count stops describing anything reachable the moment a gene panel or another dropdown is on ("`intron_variant  41,006`" over a table showing 300 rows), so each column's number is measured over the rows passing every *other* filter — panel, text boxes, the other facet columns — but ignoring that column's own selection. Ticking one consequence therefore leaves the rest of the consequence list readable; counting strictly over the visible rows would zero every sibling of a ticked value. Zeroed values grey out **in place** (`.facet__opt--empty`), because the order is R's and must not move under the cursor; the baseline moves into the option's `title` (`missense_variant — 8,412 of 41,006 rows`). Four things this rests on:
    - **The counts are accumulated inside the matching pass, not scanned for separately.** DataTables' `_fnFilterCustom` runs `ext.search` predicates in push order, each narrowing the previous result, and only *after* the global box and the per-column text boxes — so the rows the facet predicate is handed are already "everything else the reader filtered down to", the gene-panel predicate included. Per row: fail nothing → count in every column; fail exactly one → count in that column only; fail two → count nowhere. That is the whole exclude-self rule, and it costs the predicate's early return, nothing else.
    - **Which makes push order load-bearing.** Today the panel predicate is pushed at parse time (`per_sample.qmd`) and the facet predicate from the chunk inlined after it, so the order is right by accident. `attach()` splices the facet predicate to the end of `ext.search` to make it right on purpose — if it ever ran first, the counts would silently ignore the gene panel.
    - **Tokens are precomputed into a per-column CSR index** (`starts`/`ids` `Int32Array`s keyed by the DataTables row index) built once in `attach()` from `rows().indexes()` + `rows().data()`. Splitting three columns of 167k rows on *every* pass is the ~150–500 ms that made the counts static in the first place; ids also turn a count into an array increment. Splitting live is kept as the fallback for the pass that runs before `attach()` and for `tests/js/test-facet-predicate.js`, which has no DataTables instance — the two paths must agree, and the check that they do is that on load, with nothing filtered, every live count equals the number R emitted.
    - **`search.dt` is the flush point, and `attach()` forces one pass.** DataTables fires `search` at the end of `_fnFilterComplete`, immediately after the predicates have run, so no draw-ordering assumption is needed; a pass that fires it without calling the predicate once filtered everything out upstream, and the counts are then genuinely zero. The final `api.draw(false)` in `attach()` exists because `--gene-panel` means the table can already be filtered on load, and R's baseline numbers would otherwise stand until the reader touched something.
  - **The token split mirrors how the cell was built**, and the separator travels in the payload rather than being hard-coded client-side: `consequence` is comma-joined (VEP text output writes it so; `parse_vep_vcf()` rewrites the CSQ `&`) and `callers` is `paste(sort(unique(caller)), collapse = ",")` (`parse_vep_vcf()`), so ticking `missense_variant` has to match `missense_variant,splice_region_variant`. NA and `""` collapse into one `null` bucket labelled `(none)` client-side, so a literal cell value of `(none)` cannot collide with it.
  - **A facet column with 0 or 1 distinct values is legitimate, and keeps its text box.** `callers` is `""` for every row on the VEP text path (`build_variant_table()`) and the SV table has one `caller` when only Severus ran, so `js_facet_defs()` omits any column outside `[FACET_MIN_VALUES, FACET_MAX_VALUES]`, or absent from the frame, rather than offering an empty dropdown. Saying so matters — the text box left behind looks intentional, and a *renamed* facet column would otherwise vanish in silence (renaming is the hazard here as elsewhere; reordering is free) — but `js_facet_defs()`'s `message()` only surfaces outside knitr, e.g. in the test suite: the setup chunk sets `message = FALSE`, so a render swallows it. That is why each prepare chunk also publishes the **requested** column list (`window.SNV_FACET_COLS`/`window.SV_FACET_COLS`, the same vector passed to `cols`) and `facet_filter.js` `console.info`s any requested column the payload has no entry for. `info`, not `warn`: for `callers`, and for SV `caller` on a Severus-only run, it is the expected outcome, and a warning from this file means something is actually wrong.
  - **The header cell is found through the DataTables API and the index is translated, not assumed.** `api.table().header()` is the live thead (scrolling *moves* it into `.dataTables_scrollHead`), and DataTables detaches the filter cells of `visible = FALSE` columns — so the R-side full-frame index is not the DOM position. `columns(':visible').indexes()` translates it, **and the header label above the chosen cell is compared to the column name**, because a mistranslation would otherwise attach a dropdown that works and filters the wrong column. Today the two indices coincide for every facet column only because the SV table's hidden columns all sort after them in `setcolorder`.
  - **DT's own `div.form-group` is kept and the `<input>` only hidden**, because DT holds a reference to that input and its own `$td.children('div').first()/.last()` lookups have to keep finding the div. Since we never write to the input, the column's DataTables search stays empty and cannot collide with the facet filter.
  - **The dropdown menu is a child of `<body>`, `position: fixed`, and only the button is in the header cell.** The cell sits inside `.dataTables_scrollHead` and `.dataTables_scrollBody`, which clip an absolutely-positioned menu. DT ships a workaround for exactly this, for its own filter controls — a `show`/`hide` handler bound to the `div.form-group` that flips those containers to `overflow:visible` (`DT/htmlwidgets/datatables.js:474-500`) — and **it is unusable on a wide table**: `.dataTables_scrollBody` is the element holding the horizontal scroll position, so making it `visible` discards it and moves the scrollbar to a fresh `.dataTables_scroll`; the view snaps back to the first column and the menu you just opened on a right-hand column is off screen. v1.3.0 triggered that handler and had the bug. Four consequences:
    - **Fixed, not absolute, and in `<body>`, not in the cell.** Fixed alone is not enough: a fixed menu left in the cell would be duplicated *visibly* by the zero-height sizing clone DataTables rebuilds from the header's `innerHTML` on every draw — that clone clips an absolute child, nothing clips a fixed one — and ticking a value causes a draw. In `<body>` the clone only ever copies the button.
    - **`top`/`left` are computed from the button's `getBoundingClientRect()`**, aligned to its left edge, flipped to its right edge and then clamped when it would overrun the viewport, and flipped above the header when there is no room below. `.facet__menu--right` is gone: the flip is arithmetic now, not a class.
    - **A fixed menu does not travel with its button, so it is told to.** One capturing `scroll` listener on `document` (scroll events don't bubble but they do capture, so the page, the scroll body and the scroll head all reach it) plus a `resize` listener re-place it, and **close** it when the button has been scrolled out of `.dataTables_scrollHead` or off the page — a menu still pointing at a column that is no longer there is worse than no menu.
    - **Two nodes, two places, so anything that spans them has to name both**: the outside-click test (`$container` *or* `$menu` contains the target), the Escape handler, and the print rule (`.facet__menu` beside `.facet`, since hiding the widget in the header no longer hides an open menu). The `.facet-open` class that relaxed `overflow` on `.dataTables_wrapper`/`.datatables` is gone with the rest — nothing clips a fixed element.
  - **Nothing in the widget markup carries an `id`, and no handler is delegated from `document` onto a widget class.** `_fnScrollDraw` rebuilds a zero-height sizing clone of the whole header in the scroll body on every draw, refilling each cell by `innerHTML` *after* stripping ids — an id here would reappear duplicated once per draw. Hence `aria-expanded` rather than `aria-controls`, handlers bound to the created nodes, and every query rooted at the table header. Same family of hazard as the `<tr>` recycling the breakend circos's selection already works around.
  - **One more `ext.search` predicate, not `column().search()`.** Keyed on `settings.nTable` and reading raw `rowData` by name through `*_COLS`, exactly like the gene-panel predicate; OR within a column, AND across columns, and DataTables ANDs the two predicates so a tick composes with the panel and with the remaining text boxes for free. The regex alternative would re-encode the token rule in a second language with an escaping obligation (`svclass` values carry spaces, `callers` carries `clairs-to`), and an unescaped metacharacter yields a filter that matches *more* rows and raises nothing. Ticked state lives in a JS closure (exposed as `window.facetFilterState`), never in the DOM or DT's search slots, which is what makes it survive a panel change, a Scroller redraw and the header clone.
  - **`draw.dt` is now the sync point for the "N shown" line too**, not just for the breakend circos. That is also a fix: a per-column text search redrew the table but never called `updateCount()`, so `#panel-variant-count` silently went stale. `facet_filter.js` therefore needs no coupling to `per_sample.qmd` — it calls `.draw()`, and the count and the circos both follow.
- **A panel row declares which table it filters, and the interval vectors are where that is enforced.** An optional `applies_to` column scopes each gene: blank (or `both`/`all`) means both tables, `snv` the small-variant table only, `sv` the SV table only; an unrecognised value is a hard error, and a file without the column behaves exactly as before (`sarcoma` is that case). `load_gene_panel()` returns `genes` (the union, for any reader predating this) plus `genes_snv` and `genes_sv`, and — the load-bearing part — **builds `chrom`/`start`/`end`/`interval_gene` from the SV-scoped rows only**. That single subset is what scopes the entire coordinate path: `panel_intervals()`, `sv_panel_hits()`, `bnd_panel_genes()` and the JS `intervals` payload all read those vectors and needed no change. Only the *symbol* paths had to be pointed at the right set — `sv_panel_hits()`'s `has_coords = FALSE` branch reads `genes_sv` (falling back to `genes`, which is what keeps the hand-built test fixtures working), and the JS ships **two** sets per panel, `symbols` (SNV) and `symbolsSv`, so both must move together. Consequently coordinates are required only on blank/`sv` rows; an `snv` row may leave them empty. Validate `nzchar()` on the **raw** chrom column before `ensure_chr_prefix()`, which turns `""` into `"chr"` and would otherwise pass the blank check. The motivating case is the `lymphoid` panel: `IGH`/`IGK`/`TRB`/`TRA/D` are rearrangement partners worth filtering SVs on and noise in a small-variant table, and `MYD88`/`NOTCH1` are the reverse. A panel whose every row is `snv`-scoped reports `has_coords = FALSE`, because it has nothing to match an SV on.
- **A panel is a list, not a character vector, and coordinates are what SVs match on.** `load_gene_panel()` returns `list(name, path, reference, has_coords, has_scopes, genes, genes_snv, genes_sv, chrom, start, end, interval_gene, all_chrom, all_start, all_end, all_gene, has_roles, role_gene, role)` — the `all_*` vectors are every row with coordinates whatever its `applies_to` (gene-level CN; `panel_gene_intervals(p, "all")`), and `role_gene`/`role` the genes with a declared role (`panel_roles()`) — a plain list because it round-trips through Quarto's `execute_params` as YAML, which is also why an empty gene set arrives back as `NULL` and every reader of one goes through `unlist()`. Small variants always match on symbols (`genes_snv`); SVs match on **position** when `has_coords`, via `sv_panel_hits()`: a panel interval within `SV_PANEL_WINDOW_BND` (1 Mb) of either breakend of a BND, or `SV_PANEL_WINDOW_OTHER` (100 kb) of the span of any other type. Both windows are defined once, in `R/parse_severus.R`, and emitted to JS from the `panel-js-data` chunk, so the R implementation and the browser filter run the same test on the same numbers. The coordinate mode exists because **whether VEP annotates a breakend at all is a property of the sample's VEP invocation** (measured 1.6%–90% of BND rows across samples), so symbol matching hid the very `MYC`/`BCL2`/`BCL6` translocations the `lymphoid` panel is for. A symbol-only panel still works — direct hits on `gene_a`/`gene_b`, no windows — and the SV section footnote names which mode is live, so "symbol-only" can't be misread as "windows found nothing".
- **A `panel_hit` entry says how it matched, because the windows are wide enough that it has to.** Each reads `GENE (side, how)`: `side` is `A`/`B`/`span`, and `how` is `direct` when the locus overlaps the gene interval or `fmt_bp()` of the gap when it merely fell inside the window. The label originally carried only the side, and on COLO829-ONT that rendered a breakend 188.5 kb past `RB1` identically to two deletions that swallow `RB1`, `GPC5` and `PTEN` whole — proximity reading as disruption. The distance is measured from the **unpadded** locus, so `sv_panel_hits()` carries `qlo`/`qhi` through `foverlaps()` alongside the padded `start`/`end` it matches on; measuring from the window edge would report zero for everything. The symbol path is always `direct` — a VEP symbol sits on the breakend, and there is nothing to measure. With **more than one panel checked** each label gains a trailing ` [panel]` naming the panel it matched, since under a union that is all that distinguishes two hits on the same gene; with one panel there is no suffix, so a single-panel report reads exactly as it always did. `sv_panel_hits()` therefore takes *either* a bare panel object *or* a named list of them (`.as_panel_list()` tells them apart by the fields `load_gene_panel()` always sets), and `.sv_panel_hits_one()` carries the tag. As with the windows themselves, the label is built **twice**: `svPanelHits()` in the `panel-js-data` chunk fills the table's cells, and `sv_panel_hits()` is the R-side reference it mirrors — both must change together, including the suffix rule. Since the "Panel SVs" card was removed, **no render calls the R copy any more**, so a regression in it now surfaces only in `tests/testthat/test-severus.R`, not as a card visibly disagreeing with the table. That is the price of dropping a card that had gone stale against the panel chips; the tests are the check. Verified identical between the two on all 271 SV rows of CCS15-ONT, single-panel and union. JS mirrors `fmt_bp()` as `Math.round(x * 10) / 10`, not `toFixed(1)` — R prints the rounded number, so `toFixed` would render `188.5 kb` as `188.5 kb` but `306 kb` as `306.0 kb`. Verified identical on all 154 SV rows of COLO829-ONT.
- **Panel coordinates are reference-specific, and a mismatch is an error.** A coordinate-carrying TSV must declare its reference (`# reference: hg38` comment line, or a `reference` column); a declaration that disagrees with the rendered reference `stop()`s, and one that declares nothing loads with `reference = ""` and reads "unverified" in the footnote. Symbol-only panels are reference-agnostic. Builtins ship per reference (`lymphoid.hg38.tsv`, `lymphoid.t2t.tsv`) and `load_all_gene_panels(assets, reference)` presents them as one selectable `lymphoid`; a panel that ships only for *other* references is dropped with a message rather than offered. This is why `bin/render_report.R` resolves the reference **before** loading panels — reordering those two blocks back would silently pick the wrong file. Coordinate columns are all-or-nothing: a TSV with `chrom` but no `end` is an error, not a downgrade to symbol mode.
- **The main circos y-axes are drawn outside `panel.fun`, on a track index circlize is asked for — and the SV palette and y-positions have exactly one definition.** `circos.initializeWithIdeogram()` creates one track per `plotType` group *before* any of ours, so with `plotType = c("ideogram","labels")` the SV track is index 4 and the copy-number track 5, not 3 and 4; a wrong `track.index` does not error, it silently draws the scale on the neighbouring ring, which is how the SV labels ended up against the SNV dots. `get.current.track.index()` is captured after each `circos.trackPlotRegion()` instead. Drawing them inside `panel.fun` was the other half of that bug: the call ran once per sector with a fixed `sector.index`, so the copy-number scale was stamped ~23 times on top of itself (visibly heavier than the SV one) and not at all when no chromosome had segments. Outside, it is drawn once — but still only `if (nrow(cnv) > 0)`, because `parse_ascat_segments()` returns `NULL` when there is no ASCAT output and a `0..4+` scale over a blank ring reads as "copy number is zero everywhere". The axis labels come from `SV_YPOS`, which — with `SV_COLOURS` — lives in `R/parse_severus.R`, not `R/circos.R`: `severus_circos_tracks()` is what stamps both onto every row, and the tests source that file without circlize. Both were previously duplicated, and the duplicate had already drifted: `R/circos.R`'s `SV_COLOURS` was dead code while `--circos-sv-*` in `assets/styles/report.scss` mirrored *its* values, so the HTML legend rendered DEL as muted blue `#2f6db3` against a navy `#020272` ring and DUP green against red, on every report shipped. The SCSS now mirrors the one surviving constant, it is the only copy of those hex values left, and `test-severus.R` reads the `--circos-sv-*` declarations back out of the SCSS and asserts they equal `SV_COLOURS` — a wrong colour renders perfectly, so nothing else would catch the next drift. The `--sv-*` table tokens are a separate palette and stay that way: they are pale row backgrounds, deliberately not hue-matched to the ring.
- **The breakend circos is drawn in the browser, and that is what lets it re-lay-out.** `templates/sections/_sv.qmd` shows a second, BND-only circos over just the chromosomes a breakend touches, and clicking a row in the SV table highlights that row's arc. R selects the records (`bnd_links()`, `bnd_panel_genes()`) and serialises them (`bnd_circos_data()` → `window.BND_DATA`); `assets/js/bnd_circos.js` builds the SVG and **rebuilds it from scratch on every filter change**. Three things about that split:
  - **It has to be client-side, because the layout is a function of the filter.** Which chromosomes get a sector — and therefore every other sector's angular width, since they share the circle — depends on which links survive. A server-drawn SVG bakes those angles in, and circlize's arcs are flattened `<polyline>` point lists carrying no genomic coordinates, so no script can recompute them. The previous version could only *dim* arcs in place, leaving every chromosome on the plot however the panel was set. Pre-rendering one SVG per panel was the alternative and was rejected: it cannot serve `Custom…` or the per-column search boxes, which produce row subsets no pre-render anticipates.
  - **This retired the sentinel-colour tagging, and its whole failure mode with it.** The old design inlined svglite output, which emits no ids or classes, so every arc, label and gene body was *drawn* in a unique colour and the markup rewritten afterwards to attach `class`/`data-*`; a mistag downgraded the plot to a static figure, because highlighting the wrong arc is worse than highlighting none. Nodes built by `createElementNS()` carry their own attributes by construction, so there is nothing left to mis-tag. Gone with it: the `.bnd-svglite` CSS-leak rename, the `viewBox`-case repair (Quarto lowercases attributes on *markup* it processes, not on script-created nodes), and the `interactive = FALSE` fallback.
  - **The payload is row-major arrays, hand-serialised.** `js_vec()`/`js_rows()` in `R/utils.R` emit `[[...],[...]]` rather than arrays of objects, and cytobands are trimmed to the plotted sectors — 6 kB for a 4-arc plot against 70–160 kB for the SVG it replaced. Hand-rolled because `jsonlite` would be a new dependency in both `recipe/meta.yaml` and the pipeline's `environment.yml`. `js_num()` formats element-wise on purpose: vectorised `format()` pads to a common format (`c(1, 2.5)` → `"1.0"`), and scientific notation on a base-pair coordinate reads back as a different number.

  Two rules about *what* it draws. Arcs are `svclass ∈ {translocation, intra-chr breakend}` with both loci mapped — intra-chromosomal breakends are included so that every BND row a user can click has an arc, and a single breakend has no partner locus so it necessarily has none. **The gene track is the `panel_hit` column's genes**: R ships the superset (every coordinate-carrying panel's genes within `SV_PANEL_WINDOW_BND` of a drawn breakend, via the same `foverlaps()` test as `sv_panel_hits()`), and the client draws only the genes named by currently-visible rows. Two consequences that look like bugs but are not: under the default `--gene-panel none` no row has a panel hit, so **the gene track is empty on load**; and a symbol-only or custom panel produces `panel_hit` labels but no gene bodies, because it carries no coordinates. Multi-panel selection needed **no change here**: `bnd_panel_genes()` already loops every registered panel and tags each row with a comma-joined `panels` provenance string, and `rowGenes()` (`_sv.qmd`) takes the symbol by splitting a label on `" ("`, so the ` [panel]` suffix never reaches it. Gene bodies have a minimum angular width — MYC is 7 kb against a 145 Mb sector — so they are position markers, not spans to scale; their labels are de-overlapped by a two-pass greedy sweep, with a connector line showing the displacement. Selection state lives in the section's own script rather than DT's (`selection = "none"`): `Scroller` + `deferRender` destroy `<tr>` nodes on scroll, and it is re-applied from a `Set` of SV ids on every `draw.dt`.
- **The pipeline does not hand the tool its published directory; it builds a `sample_dir/` of symlinked files, and every discovery pattern must work in both layouts.** `modules/local/lrsomaticreport/main.nf` (`reportSampleDirCommands()`) links **individual files**, never directories: the VEP somatic file, the Severus VEP SV VCF, the Severus VCF and the ASCAT files **flat at the root**; the somatic VCF at the literal `variants/phased/somatic_smallvariants.vcf.gz`; QC flat into `qc/tumor/` and `qc/normal/` (no tool subdirectories); everything else at its published relative path (`signatures/assignment/…`, `shatterseek/<combo>/`, `ecdna/coral/…`, `variants/savana/`, `vep/SVs/`, `padfoot/<combo>/`, `reconplot/<combo>/…`). Of Wakhan it stages only `solutions_ranks.tsv` and the rank-1 `integer_profile.bed` and `genes/genes_copynumber_states.bed`, read through `solution_rank_1` — **no HTML**, so nothing may depend on Wakhan's plots or heatmap existing. Two consequences: `list.files(recursive = TRUE)` sees symlinked files but does **not** descend into a symlinked directory (which is exactly what `wakhan/solution_rank_<n>` is in the published layout), and a pattern that leans on a directory name must use one the staging reproduces. When a new tool output is added here, the pipeline's staging channel (`workflows/lrsomatic.nf`, `report_leg`) needs the same file, or the section renders "not run" in every pipeline report while working on every published directory you test against. The discovery tests that matter have a staged-layout twin (`test-cna.R`, `test-instability.R`, `test-reconplot.R`, `test-qc.R`).
- **Copy number has one segment source, and purity/ploidy follow it.** `R/sections/cna.R`: segments are Wakhan's rank-1 `integer_profile.bed` (haplotype-resolved: `cn_a`/`cn_b` = HP1/HP2), else ASCAT's `segments_raw.txt` (`nMajor`/`nMinor`). The purity and ploidy used for the calls are **those of the same source** — calling Wakhan segments at ASCAT's ploidy puts the thresholds on a different scale from the copy numbers — and every source found is still listed (`purity_by_source`: Wakhan, ASCAT, SAVANA), because they genuinely disagree; the overview flags a purity spread ≥ 0.15. Wakhan's purity is `cell_purity` (the fraction of tumour cells, the quantity ASCAT and SAVANA estimate), not `dna_purity`. Wakhan segments without a solutions table get the length-weighted mean autosomal CN as ploidy, flagged `ploidy_estimated`. The rest:
  - **Calls are the COSMIC CGC CNA definition**, constants at the top of `cna.R` (`CNA_PLOIDY_SPLIT` 2.7, `CNA_AMP_CN_LOW` 5, `CNA_AMP_CN_HIGH` 9, `CNA_LOSS_OFFSET` 2.7) and printed by `_cna_genes.qmd`; above the split the deletion threshold (CN < ploidy − 2.7) fires on CN 1 from ploidy 3.71, so a non-zero call there is `deep deletion` (same tier, token `homdel`), and only CN 0 is `homozygous deletion`; gain/loss is against `round(ploidy)`, and against `max(1, round(ploidy / 2))` on chrX/chrY **in a male** (`cna_expected_cn()`), which is what keeps a male's single X from reading as a loss and as LOH. `--sex` is therefore load-bearing for CN; when ASCAT's `metrics.txt` inferred the other sex, `_cna_genes.qmd` warns.
  - **A gene that no segment overlaps has `call = NA`** (`foverlaps(nomatch = NA)`, `n_segments == 0`), shown as "no segment" — never "neutral".
  - **`integer_profile.bed`'s header is the last leading `#` line**; the ones above it are a prose legend (`read_hash_header_table()`). Taking the first `#` line as the header reads the legend as column names.
  - **Wakhan files are found by literal `file.path()`, never by listing** (`locate_wakhan_solution_file()`, `R/parse_ascat.R`): `solution_rank_<n>` (0.5.0), `solution_<n>` (0.4.x), then `repository_name`. Both rank names are symlinked directories, which a recursive listing skips. The Wakhan dir itself is `sample_dir/wakhan`, else wherever a `solutions_ranks.tsv` was listed.
  - **Wakhan's per-gene file is a fallback only**, for list genes without coordinates (source "Wakhan gene file"); rows with a haplotype state above `CNA_MAX_PLAUSIBLE_CN` (100) are dropped and counted — P15 has a state-394 row at ~3,300× "adjusted coverage". Gene spans otherwise come from the list's own coordinates, **all rows regardless of `applies_to`** (`panel_gene_intervals(p, "all")`); in `lymphoid` the `sv`/both rows' spans come from the NHL beds and the `snv` rows' from GENCODE / Liftoff (`assets/gene_lists/README.md`), so the spans in one file come from two annotations, two lists can carry different spans for one gene, and `kf_cna_rows()` merges per gene and call.
  - **The report embeds a static profile instead of Wakhan's Plotly HTML** (`cna_profile_plot()` via `embed_svg_plot()`): the iframes were tens of MB per report. Segments narrower than `CNA_PROFILE_MIN_FRAC` of the genome are widened so focal events stay visible, and values above `CNA_PROFILE_YCAP` are marked at the cap. Only rank 1 is drawn unless `--embed full`; the footnote points at `wakhan/` in the pipeline output for the interactive plots. The old iframe helpers, the CN-plot lookup and `test-wakhan.R` are deleted.
  - WGD = major allele ≥ 2 over more than half of the autosomal length covered by segments; LOH fraction = autosomal length with no minor allele on a non-zero segment (`cna_genome_metrics()`). ASCAT's own WGD/LOH/GI from `metrics.txt` — a generic filename, so only the one beside and prefixed like the purityploidy/segments file is taken — are shown beside them, and a WGD disagreement flags the biomarker.
- **The overview is computed in R for every embedded list and filtered in the browser.** `build_overview()` (`R/key_findings.R`) runs in the setup chunk after every section, on the **full** `variant_table`, and tags each finding with the comma-joined lists whose gene set holds the gene — per table: small variants against the list's SNV scope (`panel_snv_genes()`), SVs against its SV scope (`sv_panel_hit_table()`), CN against its gene-level rows. **The table is one row per gene**: `build_findings()` orders the findings so a `gene`'s rows are contiguous (group best tier, gene, tier, type), and `_overview.qmd` emits one `<tbody class="kf-group" data-gene data-genes>` per gene with one `<tr data-panels data-tier data-type>` per alteration. `assets/js/key_findings.js` shows the lines whose lists intersect the ticked chips, or whose group's `genes` hold a typed Custom… gene; a group shows when any line does, its first shown line (the best tier, since R sorted by tier) becomes `.kf-row--head` and alone prints tier, gene and the union of shown lines' lists (`.kf-row--cont` hides them with `visibility`, so columns keep their width), and tbodies are re-appended by best shown tier. Re-appending only when the order changed is what keeps `apply()` idempotent. `per_panel_n` counts genes, not lines. The rules a reader sees are in the README and in the "How key findings are chosen" footnote; both must change with the constants. Traps:
  - **Nothing ticked means no findings**, not all of them (`state.all`): without a list the table would be every HIGH-impact variant in the genome. The empty state shows per-list tier 1–2 counts (`per_panel_n`) as buttons that tick the chip through its own `click()`, so the tables follow too.
  - **`window.registerPanelListener()` calls a listener at least twice per change** (`syncControls()` and `redraw()`), and immediately when registered after the first sync; `apply()` is a pure function of `(state, showLow)` for that reason. The gene-level CN table (`_cna_genes.qmd`) is the other listener and follows the same rule.
  - **Rows outside every list exist only for Custom…**: ClinVar (likely) pathogenic or HIGH-impact small variants, capped at `KF_MAX_NONPANEL` (500), strongest first, `panels = ""`. SV and CN findings are never computed outside a list.
  - **`sv_panel_hit_table()`'s `direct` is not trusted for findings.** For a DEL/DUP/INV/INS it means "the span overlaps the gene", so a 200 Mb inversion is a direct hit on every list gene of the arm. A span hit counts only when a breakpoint lies in the gene (`kf_bp_in_gene()`) or the event is a DEL/DUP of at most `KF_FOCAL_SV_MAX` (3 Mb) covering it; otherwise it is dropped and left to the CN rows. The panel filter and `panel_hit` labels keep the wide meaning — they answer a different question.
  - **Two demotions that look like bugs but are biology.** A CN call in a **pseudoautosomal region** (`KF_PAR`, per reference) is tier 3: reads from the X and Y copies map to one of them, and CRLF2 on a real T2T sample read CN 0 with nothing deleted. At an **IG/TR locus** (`KF_RECOMBINING_LOCI`) a CN loss and any non-translocation SV of locus size (≤ 3 Mb) are tier 3 — V(D)J recombination deletes DNA in every lymphocyte — while a translocation keeps its tier, since an IG partner is the point.
  - **SV calls are never summed across callers** — Severus and SAVANA report the same rearrangements. `kf_sv_events()` matches calls of *different* callers whose breakpoints both agree within `KF_SV_SAME_EVENT_BP` (1 kb; on one contig also within half the smaller event, so two neighbouring 300 bp deletions stay apart), transitively, into events; an untyped call takes its event's typed class, so Severus' "intra-chr breakend" matching SAVANA's DEL is a deletion — on CCS15-PB that was CDKN2A listed three times (two SV calls 1 bp apart plus the CN loss) and CDKN2B carrying a tier-3 "near" row from Severus' copy of the deletion that covers it. Findings collapse per (gene, event group); the `"N events"` suffix counts events, the callers named are those of the row's events (not only of the calls that hit the gene), and the proximity-redundancy test compares event ids, not raw ids. Untyped Severus junctions with no match still group with SAVANA's "INV". This is key-findings only: the SV table, circos and panel filter still show each caller's call. The SV biomarker lists per-caller counts.
  - **A rearrangement joining two listed genes is one row** (`kf_merge_sv_partners()`): strong junction rows of different genes in the same event group that share an event merge into `gene = "EWSR1–ATF1"` (en dash: 5′/3′ is not established, so not HGNC `::`), ordered by Padfoot's listing, else chromosome; `genes = "EWSR1,ATF1"`, best tier, union of panels. Every other row has `genes == gene`. Anything that keys on `gene` as a symbol (the LOH tagging in `build_findings()`, `kf_gene_roles()` lookups) does not see the members of a joined row; the row's role is `""`.
  - **Roles come from the lists** (`kf_gene_roles()`): disagreeing lists give `both`, which adjusts nothing. `kf_tier()` is pure and vectorised over `type` / `+`-joined evidence tokens / `role`; `kf_tier_note()` explains an adjustment in the evidence text. The token string is the interface between the evidence builders and the tiering — add a rule as a token, not as a special case in a builder.
  - **Tumour-only** (`ctx$outputs$mode`): a caveat above the table, since small-variant findings can be germline. `variants/clairsto/<id>.verdict_status.tsv` (`outputs$verdict_status`, `parse_verdict_status()` → `OVERVIEW$verdict`) adds a warning there and in the small-variant section when Verdict was `skipped` (`not_run`: a short note; `applied`/absent: nothing) — `verdict_note()` is the one wording.
  - In a data.table `[`, a local named like a column means the column: `kf_bp_in_gene()` copies `gene[i]` to `want` outside the brackets for that reason.
  - The print layout (`assets/styles/_print.scss`, imported last) puts hero + key findings + biomarkers on the first A4 page(s); `.kf-print-panels` prints which lists were ticked, and `.overview-print-footer` carries "Research use only" and the version.
- **Mutational signatures: MatrixGenerator's channel order is not the plotting order, and a flagged context never reaches the overview.** `R/sections/signatures.R`. `*.SBS96.all` is sorted alphabetically by 5′ base (`A[C>A]A, A[C>A]C, …`), not by substitution class; `parse_sig_matrix()` reindexes every matrix on `sig_channels()` (the standard COSMIC order, every channel present, unknown channels dropped with a message) — plotting the file's order looks plausible and is wrong. A context is flagged `few_mutations` below `SIG_MIN_MUTATIONS` (200 SBS / 50 DBS / 100 ID) and `poor_fit` below `SIG_MIN_COSINE` (0.9); `sig_dominant()` takes signatures ≥ `SIG_DOMINANT_MIN_PCT` (5%) from **unflagged contexts only**, and only `dominant` feeds the overview. That is deliberate: long-read ID fits sit just under the cosine threshold (P15 0.893, AITL6 0.888) — homopolymer indel noise, fitted against COSMIC's **GRCh37** ID83 set whatever the reference — and must not surface as a "dominant" MMR signature. The aetiology lookup (`assets/signatures/cosmic_v3.6_aetiology.tsv`) is conservative by design (uncertain → "Unknown"), a signature missing from it reads "not in lookup" (`in_lookup = FALSE`), never an error, and a COSMIC version without its own file falls back to the highest bundled one with a message. The highest `COSMIC_v<ver>` directory wins, compared with `numeric_version()` (3.10 > 3.6). Matrix filenames carry a sanitised sample name, so a stem match is a tie-breaker only. Without `Assignment_Solution_Samples_Stats.txt` the cosine is NA and raises no poor-fit flag.
- **Genome instability: "ran and found nothing" is a result, and each tool says so differently.** Both modules return `list(status = "not_run")` rather than `NULL` when nothing was found.
  - **ShatterSeek** (`R/sections/shatterseek.R`) runs once per SV/CN caller combination (`severus_ascat`, `severus_wakhan`, `savana`; the rows' own `cn_source`/`sv_source` win over the directory name), and the combinations can **disagree**. All are shown — as **one** table, a row per (chromosome, combination) with a Combination column when several ran, and a footnote naming the combinations that called nothing; no tabs, because three tabs each saying "no chromothripsis" was the bloat this replaced. With no call anywhere the section is just `shatterseek_verdict()`'s single sentence, which names every combination and the chromosomes tested. `shatterseek_disagree()` flags the biomarker when their called chromosome sets differ, and nothing picks a winner. A chromosome counts as called at any `chromothripsis_confidence` other than `none`. Columns go through `SHATTERSEEK_COLUMNS` / `resolve_columns()`. Each call names its tiers (`shatterseek_tiers()`); the section and the overview card are rendered once per minimum-tier setting (`SHATTERSEEK_MIN_TIERS`, `shatterseek_at_tier()` on the call's best tier; `[data-ss-min]` views, every `.ss-tier-select` kept in step by the script in `_instability.qmd`, which also sets `window.ssMinTier` and fires `ss-tier`).
  - **ecDNA** (`R/sections/ecdna.R`) has four statuses. `none_detected` covers a **0-byte `*_CNV_SEEDS.bed`** — CoRAL found nothing above its gain threshold, which is a negative result (AITL6), not a missing file — and a classifier that kept no amplicon after dropping "No amp/Invalid". `unclassified`: CoRAL ran but there is no AmpliconClassifier output (a CHM13 run without `--aa_data_repo`, or `--skip_ampliconclassifier`), so ecDNA status is unknown — shown as a warning, never as "none". `detected` means AmpliconClassifier found **an amplicon, not necessarily ecDNA**: read `n_ecdna`/`n_bfb`. When neither is above 0 (`ec_neg` in `_instability.qmd`; CCS15-PB's one `No-FSCNA` amplicon) the verdict line stands alone and the amplicon table and CoRAL plots go into a collapsed callout — which is why those two chunks are `results='asis'` through `inst_html()`: raw HTML inside a callout fence. CoRAL's `cycles/` summary wins over `reconstruct/`. `_gene_list.tsv`/`_result_table.tsv` are generic suffixes, so they are accepted only under `ecdna/` or `amplicon_classifier/`; `<id>_coral_cn.bed` is CoRAL's input and ignored.
- **SVs come from two callers with different VCF dialects, listed side by side and never merged.** `parse_sv_vcf(f, caller)` reads both through `SV_CALLER_DIALECTS`: mate key `MATE_ID` (Severus) vs `MATEID` (SAVANA); VAF `FORMAT/VAF` vs `INFO/TUMOUR_AF` (Number=2, first value = this breakend's); support `FORMAT/DV` vs `INFO/TUMOUR_READ_SUPPORT`. **SAVANA writes every rearrangement as a BND pair**, stating the junction in `BP_NOTATION`; same-chromosome pairs are typed through `SV_ORIENTATION_TYPES` (`+-` DEL, `-+` DUP, `++`/`--` INV) and become spans exactly like Severus' own DEL/DUP/INV — size, 100 kb panel window, contiguous circos ring, no breakend arc. Untyped, ~1,150 of P15's 1,246 SAVANA pairs (small deletions) were "intra-chr breakends" with 1 Mb windows. `svtype_raw` keeps the VCF's `BND` (hidden column, footnoted). Further:
  - `R/sections/sv.R` rbinds both callers with a `caller` column. **`id` is unique across callers** — within a caller via `make.unique()`, and a caller whose ids collide with an earlier one's is prefixed `<caller>:` as a whole — because row selection and the breakend circos key on it. Padfoot is joined **before** that prefixing, on the caller's own ids.
  - **One caller drives the genome-wide circos** (`circos_caller`: Severus when it has records, else SAVANA); `n_by_caller` and the SV biomarker give per-caller counts. Counting over `table` counts a rearrangement once per caller — take `table[caller == circos_caller]` for a single figure.
  - SAVANA's somatic calls are the `*.pon_filtered.classified.somatic.vcf` where it exists (PacBio tumour-only — what VEP, Padfoot and ReConPlot were fed), else `*.classified.somatic.vcf`; never `classified.vcf` (somatic + germline), the germline file or a lenient/strict variant. `_SV_VEP.vcf.gz` and `_VEP_SAVANA.vcf.gz` cannot match each other.
  - **VEP may give breakend pairs no gene symbol at all**: on P15, none of the BND-derived rows of either caller carries one — for SAVANA that is every DEL/DUP/INV/translocation, leaving only its INS annotated. Panel matching and SV findings are positional for that reason, and a SAVANA-typed DEL with a breakpoint in a list gene and no Padfoot rating reads "exon effect not annotated" (tier 2), not "intronic".
  - **Padfoot's SV ID is a different key per caller**: Severus reports a pair under its `_1` record, SAVANA under the shared stem (`ID_1` for `ID_1_1`/`ID_1_2`). `join_padfoot()` tries id, mate id and id stem and picks **one key for the whole table** (most matches; ties id > mate id > stem), falling back to breakend loci in either orientation only when no id key matches — the footnote then says so. Per-row key choice would silently join the two sides differently. The `padfoot_*` columns exist only when some Padfoot file was found (`severus_wakhan` for Severus, `savana` for SAVANA).
  - ReConPlot (`R/sections/reconplot.R`) takes PNGs only, matched on the path `reconplot/<combo>/{genome_wide,per_chromosome,focus}/`. **Slim mode embeds no genome-wide figure** (10200×1200 px: about 130 px tall at page width, unreadable) and only the per-chromosome figures `reconplot_chromosomes()` selects, one set shared by every combo tab. Two kinds of reason: **always shown** — a ShatterSeek call (any combination, any confidence but `none`) or an SV with a Padfoot cancer-gene rating, any `HIGH_` class (`RECONPLOT_PADFOOT_IMPACT`: `HIGH_ONCO`, `HIGH_TSG`, open-ended as in `_sv.qmd`; the README and both `_reconplot.qmd` captions name the two, keep them in step; plain `HIGH`, score 3, is deliberately excluded: on CCS15-PB it selected 12 chromosomes for USH2A, PRSS2, MACROD2 and other fragile-site genes, while `HIGH_ONCO` picked out exactly ALK, CDKN2A, EWSR1–ATF1, NSD3, PRKN and CNTNAP2) — and **list-dependent**, a tier 1–2 SV or CNA key finding, whose chromosomes are parsed out of `findings$locus`. The list-dependent figures carry `data-panels`/`data-genes` and are shown by an inline listener through `window.keyFindings.kfRowMatches` (looked up per call — `key_findings.js` is inlined after the section), so they follow the chips exactly as the overview does; every candidate is embedded, hidden or not. Each caption names its reasons. Slim mode embeds at most `RECONPLOT_MAX_CHROMS` (12) chromosomes, ranked by `reconplot_cap()` on `priority` (D CCS15-ONT, 23 chromosomes × 3 combos of mostly whitelist-rescued SV findings, was 69 PNGs / 5.4 MB); the footnote names the chromosomes left out. `--embed full` embeds every figure and ignores the selection. `reconplot_chromosomes()` also returns `kinds` (chromothripsis / padfoot / finding), `ss_tier` and `priority`; the figures carry `data-kinds`/`data-ss-tier`, and the section's script shows a figure when a ticked reason applies (chromothripsis at or under `window.ssMinTier`, Padfoot always, a finding through `kfRowMatches`). `focus/` PNGs (the pipeline's `--reconplot_regions`/`--reconplot_genes`) are `combos[[cb]]$focus`, always embedded, as a "Your regions" block that opens the section; the per-chromosome figures then sit in a collapsed callout.
- **Slimming: `variant_table` is the full table and `variant_embed` is what the HTML carries — every count reads the first.** `slim_variant_table()` keeps HIGH/MODERATE impact, ClinVar (likely) pathogenic, and any symbol in a list's SNV genes; TMB, `n_vaf`, `n_multi`, the small-variant counts and the overview all read `variant_table` (or `vep_data`), only the DT, `SNV_COLS` and the facet payload read `variant_embed`. The full table always goes to `<sample-id>_small_variants.tsv.gz` (`write_full_variant_table()`, list columns dropped) — written by the setup chunk next to the `.qmd` (knitr's working directory) and moved beside the HTML by `bin/render_report.R`; the pipeline emits it as its own output. Traps:
  - **Row subsetting drops custom attributes**, including `vep_fields` (the Annotation sources footnote) — `slim_variant_table()` copies them back and adds `n_full`/`n_embedded`. Any new subset of a variant table has to do the same.
  - **ClinVar is matched by token, never by substring** (`clinvar_is_pathogenic()`): `Conflicting_classifications_of_pathogenicity` contains "pathogenic". Cells are split on `,` `&` `/` `|`, a leading `_` is dropped (`Pathogenic,_low_penetrance`), case-insensitive (the cache's `CLIN_SIG` is lower-case, the plugin's capitalised). The key findings use the same function.
  - **A scoped list with an empty SNV set contributes no genes** (`panel_snv_genes()`): with `has_scopes`, `genes_snv` is used even when it came back from YAML as `NULL`. Falling back to `genes` there would put the SV-only `IGH`/`TRB`… into the slim set and the SNV findings.
  - Other secondary figures follow `embed` too: ASCAT diagnostics, Wakhan ranks > 1, ReConPlot per-chromosome figures, CoRAL plots beyond six. Each slim omission says where the rest is.
- **The genome circos draws SNV density, not SNVs**, because one point per SNV was 5–9 MB of SVG. `bin_snv_density()` (circlize-free, in `R/parse_smallvariants.R`, so testable) counts unique single-base substitutions per `CIRCOS_SNV_BIN` (1 Mb) window, every window present; the y cap is the 99th percentile of non-empty windows (`circos_density_cap()`), so one kataegis window cannot flatten the rest, and `_circos.qmd` recomputes it with the same helpers to name it in the caption. The track is **one plain `polygon()` per chromosome in canvas coordinates** (`circlize()` → x/y), with flat runs thinned and every 10th baseline vertex kept — `circos.lines(area = TRUE)` subdivides every segment along the arc and tripled the track's SVG weight. `circos.par("unit.circle.segments" = 200)` (default 500) shrinks every arc in the SVG, since circlize flattens arcs into point lists. The copy-number ring is the `cna` section's own segments (`circos_cn_segments()`, `R/parse_ascat.R`: Wakhan rank 1, else ASCAT, capped at 4, major/minor = the higher/lower of `cn_a`/`cn_b`), named in the caption; it used to be ASCAT's `parse_ascat_segments()` whatever the overview used, and vanished under skip_ascat. ASCAT's raw segments are only the fallback when there is no `cna` section.
- **The genome circos labels the overview's drivers, and the labels are drawn in the browser** so they follow the chips. The circos itself stays a static svglite `<img>`; `assets/js/circos_drivers.js` writes labels into an overlay `<svg class="circos-drivers">` that shares its viewBox. Pieces:
  - **Which genes**: `circos_driver_rows()` (`R/key_findings.R`) — every tier 1–2 (`CIRCOS_LABEL_TIERS`) finding line, one row per member gene, so a joined `EWSR1–ATF1` row labels both partners at their own loci. Non-panel rows are kept for a typed Custom… list. The JS keeps the rows `window.keyFindings.kfRowMatches()` accepts — the overview's own predicate, so the circos and the table can never list different genes — and collapses them to one label per gene at its best tier (bold ink for tier 1, muted for tier 2). Nothing ticked means no labels, with a hint in their place.
  - **Where**: `circos_label_loci()` — the midpoint of the gene's first interval in any list (`panel_gene_intervals(scope = "all")`, so an `snv`-scoped row counts), else its gene-level CN row, else its first small variant; a gene with none gets no label. This is why `draw_circos()` now runs **after** `build_overview()` in the setup chunk.
  - **Anchors are read off the open device**, not recomputed: `draw_circos(label_loci = …)` maps each locus through `circlize()` and `grconvertX/Y(..., "user", "device")` before `dev.off()`. svglite's device units are its viewBox units with y already pointing down (checked empirically; `test-circos.R` pins it), so the browser draws on the image exactly. It returns `list(path, anchors, geometry)`; `theta` is circlize's (degrees, counter-clockwise from 3 o'clock, not normalised — 419.8 is fine). With any label candidate the canvas widens to `CIRCOS_LABEL_CANVAS` (±1.34) to leave a ring outside the chromosome names, which shrinks the circle; the plate's max width rises from 680 to 760 px to compensate.
  - **Placement** (`placeLabels()`, exported and tested in `tests/js/test-circos-drivers.js`) is cluster-centring, not `bnd_circos.js`'s one-directional push: overlapping runs merge into one group laid out evenly around the mean of its genes, repeated until nothing overlaps, so a crowded cluster stays centred on its loci. The seam is at 12 o'clock, inside the plot's wide gap.
  - The viewBox is set from JS, not written in the markup: Quarto lowercases attributes on markup it processes, and an SVG `viewbox` is ignored. Label colours are fixed ink, not theme tokens — the plate stays light in dark mode.
- **Light/dark is a toggle, and every dark rule goes through one mixin.** `@mixin dark-mode` (`report.scss`, `scss:defaults`) emits its content twice: under `@media screen and (prefers-color-scheme: dark) { html:not([data-theme="light"]) … }` and under `@media screen { html[data-theme="dark"] … }`. The header button (`_header.qmd`) sets `data-theme` on `<html>` and stores it in `localStorage` (`lrsomatic-report-theme`); a one-line `include-in-header` script in `per_sample.qmd` re-applies it before first paint, so a dark pick does not flash light. Rules: **never write a raw `@media (prefers-color-scheme: dark)` block** — it would ignore the toggle; inside the mixin write custom properties as bare declarations (the content is scoped under `html`, which is `:root`, so a nested `:root { }` would match nothing); and both forms are `screen`-only, so a printout is always light (it used to follow a dark OS setting). The compiled CSS (URL-encoded in a `data:` link) should hold equal counts of `html[data-theme=dark]` and `html:not([data-theme=light])`.
- **Page width is Quarto's grid, not a `max-width`.** With `toc: left`, Quarto's `.page-columns.toc-left` grid caps the content column at `calc(800px - 3em)` plus a 200px margin column, whatever `page-layout` says, and gives the rest to `5fr` gutters. `report.scss` overrides `grid-template-columns` for `#quarto-content.page-columns.toc-left` at ≥ 992px (margin columns folded away, content up to `$content-max`), keeping every line name Quarto places things by. A `max-width` on `.page-full > .column-body` — what the report had before — matches no element in the rendered page.
- **Verified on real pipeline output, not only fixtures.** The v2 sections were checked against full-layout dev outputs: P15 (`pilot15`, ONT tumour-only, CHM13: Wakhan 0.5, SAVANA, Severus, signatures, ShatterSeek), AITL6 (PacBio tumour-only, CHM13: ReConPlot, 0-byte ecDNA seeds, VEP plugins, cramino 2.0) and CCS15-PB (clear cell sarcoma); the integration render set also covered CCS15-ONT and DLBCL7. **The acceptance case is CCS15-PB under `--gene-panel sarcoma`: the EWSR1–ATF1 translocation must be one tier-1 finding covering both genes** (row `EWSR1–ATF1`, `genes = "EWSR1,ATF1"`; it is reported by both callers and rated `HIGH_ONCO` by Padfoot), and CDKN2A must be one gene with two lines — the SV deletion naming both callers and the copy-number loss. Ask for the current locations of these directories rather than trusting a path recorded anywhere: scratch copies are purged. Slim renders of those five were 4.5–6.4 MB (CCS15-PB 6.2 MB; 15 MB with `--embed full`) — a jump well past that means something is embedding what slim mode should leave out. From 2.0.0rc2 CCS15-PB under `--gene-panel sarcoma --gene-panel lymphoid` is 7.1 MB: the three dropped genome-wide ReConPlot strips were ~1 MB, the 27 per-chromosome figures replacing them (9 chromosomes × 3 combos) ~1.7 MB.

## R package requirements

`recipe/meta.yaml` is the source of truth — it is what the Bioconda package is built from,
and `container/environment.yml` (the image's pinned copy of the same list) must name the same
packages: `container/check_deps.py` fails the container workflow when they drift. The
pipeline's `LRSOMATICREPORT` module has no conda environment of its own any more — it runs the
published image (`ghcr.io/ljwharbers/lrsomatic-report:<version>` or the `-sif` ORAS artefact)
and refuses conda profiles — so a version bump here is a container-tag bump there. Do not add a
dependency without adding it to both files; v2 added none (`jsonlite` in particular is
deliberately absent — JS payloads go through `js_vec`/`js_rows`/`js_num`/`js_quote`).

```r
install.packages(c("data.table", "dplyr", "DT", "htmltools", "optparse",
                   "quarto", "yaml", "ggplot2", "svglite", "knitr",
                   "R.utils", "base64enc"))
BiocManager::install("circlize")
```

`R.utils` is never called directly; `data.table::fread()` needs it for gzipped input.
`svglite`, `base64enc`, `knitr` and most `ggplot2` calls are used namespaced (`R/utils.R`,
`R/sections/cna.R`, `R/sections/signatures.R`, `templates/sections/_qc.qmd`) rather than via
`library()`, so grepping for `library(` under-reports the real dependency set; grep for `pkg::`
too. `grid`, `grDevices`, `stats`, `tools` and `utils` are base R.

Tested with R 4.4.1 and Quarto 1.5.57.

Fixtures live in `tests/fixtures/<area>/` (`cna`, `instability`, `overview`, `qc`,
`signatures`, `sv`), a few kB each; the signature fixture is P15's real MatrixGenerator / SigProfilerAssignment output. `setup.R` sources the `R/`
files under test — including every `R/sections/*.R` (via `section_files()`, in parse order),
which must come after `R/sections.R` because `register_section()` runs at source time, and
`R/key_findings.R` after them. Nothing under test needs `circlize`
(`R/circos.R`, the one file that does, is not sourced), so the suite runs without it.
`test-cli.R` asserts that `VERSION` equals the recipe's version and that `--help` lists every
flag the pipeline passes, `--embed` included. One test reads a real sample directory
(AITL6's 0-byte ecDNA seeds, `test-instability.R`) and skips when it is not mounted.

```bash
Rscript -e 'testthat::test_dir("tests/testthat")'
```

Run it from the repository root — `setup.R` derives `repo_root` from
`dirname(dirname(getwd()))`, so it relies on testthat setting the working
directory to `tests/testthat`.

Two JS tests, run with plain `node` and no dependencies (the repo has no JS toolchain, and a
test framework would be a new dependency for nothing):

```bash
node tests/js/test-facet-predicate.js
node tests/js/test-key-findings.js
node tests/js/test-circos-drivers.js
```

`test-key-findings.js` `require()`s `assets/js/key_findings.js` directly — the file exports its
pure predicates (`kfRowMatches`, `kfSummarise`, `kfListLabel`) when `module` exists and skips
its DOM half when `document` does not — and covers list sets, custom genes, the nothing-ticked
state, tier-3 collapsing and idempotence under repeated listener calls.

`test-facet-predicate.js`:

It stubs jQuery just enough to load `assets/js/facet_filter.js`, captures the pushed
`ext.search` predicate and drives it directly — covering the part of the widget that fails
*silently*, since a wrong token split shows the wrong rows rather than erroring. It reaches
the ticked state through `window.facetFilterState` and the live per-value counts through
`window.facetFilterCounts()`, which fail the same way — a wrong number reads as a wrong
number. It drives the predicate with an explicit 5th argument, DataTables' per-predicate
loop counter, because a scenario's first row (`j = 0`) is what resets the counts.
Everything DOM-shaped in that file (menu placement and clipping, keyboard behaviour, the
header cell replacement, the count repaint) is still only checkable by rendering a report
and clicking, and any `console.warn` from `facet_filter.js` in the browser means a filter
silently fell back to a text box. The CSR token index has no offline test either: the check
on it is that on load, unfiltered, every dropdown count equals the number R rendered.

No CI runs either suite: `.github/workflows/container.yml` only checks the dependency lists
(`container/check_deps.py`) and the recipe digest (`container/check_sha256.sh`), builds the
image and runs `container/smoke_test.sh` — `--version`, `--help` flags, a render of
`tests/fixtures/test_SOMATIC_VEP.vcf.gz` (report and `*_small_variants.tsv.gz` sidecar) and
`--gene-lists-dir` — on pull requests touching the tool and on `v*` tags. The two suites and a
full render on real data are the checks that matter; run them by hand.

## Releasing

`VERSION` is the single source of truth (`--version` prints it); `recipe/meta.yaml`'s version
must equal it (`test-cli.R`, `check_sha256.sh`) and the git tag must be `v<VERSION>` (the
workflow refuses otherwise). Conda versions cannot contain `-`, so a pre-release is `2.0.0rc1`,
not `2.0.0-rc1` — and the image tag is the same string. The recipe's `sha256` can only be
recorded after the tag exists: the release commit keeps the previous digest and a follow-up
commit records the new one (`check_sha256.sh` is a no-op until the tag's tarball exists).
